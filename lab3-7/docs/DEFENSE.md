# Подготовка к защите ЛР3, вариант 27

**Цель:** реализовать первую рабочую версию архитектуры ЛР1/ЛР2: отдельные компоненты,
7 БД, GraphQL Query, сервисы и mock-вызовы. Полноценный Kafka/gRPC на этом этапе запрещён
условиями методички — их реализация оставлена на следующие работы.

## Текст для устного объяснения (2 минуты)

«В первых лабораторных я спроектировал систему онлайн-репетиторства:
семь сервисов, каждому соответствует собственная база, GraphQL как единый внешний
интерфейс, gRPC для синхронных запросов и Kafka для событий. В третьей лабораторной
перевёл проект в исполняемый код. Базы создаются отдельными с разными пользователями,
DDL перенесено из ЛР2, а тестовые записи позволяют проверить типовые сценарии.

Внешний API реализован в FastAPI с Ariadne, при этом исходная GraphQL-схема ЛР2 сохранена.
Для каждого Query есть resolver. Resolver проверяет контекст и делегирует задачу через
MockRpcPorts конкретному сервису. Бизнес-данные сервис получает SQLAlchemy только из
своей БД. На примере поиска преподавателей можно показать фильтрацию по предмету,
цене, рейтингу, сортировку и связанную загрузку предметов и рейтинга.

Взаимодействия с реальными gRPC-запросами пока заменены mock-адаптером без сетевого
обмена — такой этап прямо указан методичкой. Реальный Kafka и Mutation пока не
реализованы. Проверил роли, пустые результаты, некорректные параметры, вложенные поля,
семь БД и возможность запуска автотестов.»

## Что показать последовательно

1. `docker compose ps`: PostgreSQL и Gateway в состоянии Up.
2. `http://localhost:8000/ready`: 7 баз отмечены `ok`.
3. `db/schemas/t_database.sql` и `db/init_all.sql`: исходная структура и создание БД.
4. `contracts/schema.graphql`: 14 Query + 14 Mutation из ЛР2 без перепроектирования.
5. `app/gateway/schema.py`: resolver `teachers` и проверки входных параметров.
6. `app/transport/mock_ports.py`: метод SearchTeachers имитирует будущий gRPC контракт.
7. `app/services/catalog.py`: запрос только к своей БД `tutor_t`.
8. `demo/queries.graphql`: каталог, личные записи ученика, расписание преподавателя, аналитика администратора.
9. Запрос `users` токеном ученика: FORBIDDEN, токеном администратора — данные.
10. `docker compose exec -T gateway pytest -q`: автоматические проверки.

## Почему выбраны технологии

- Python 3.11: простая читаемая реализация разделённых модулей и тестов.
- FastAPI: ASGI-приложение, health-check и подключение GraphQL.
- Ariadne: schema-first,использует неизменённую SDL ЛР2.
- SQLAlchemy Core: безопасные SQL с bind-параметрами; SELECT не спрятан в GraphQL.
- PostgreSQL: семь **отдельных БД**, а не семь схем одной общей БД; локальные FK.
- Docker Compose: воспроизводимая установка на Windows, без ручного создания таблиц.

## Частые вопросы преподавателя

**Почему нет реального gRPC?** ЛР3 прямо требует заглушки; мы создали адаптер с названиями методов из `tutoring.proto`. В ЛР4+ адаптер меняется на gRPC-клиент.

**Почему сервисы не в 7 отдельных контейнерах?** На этапе ЛР3 они реализованы семью логически изолированными пакетами с отдельными БД и раздельными репозиториями. Взаимодействие задано локальным mock, как требует методичка. Разнос в отдельные процессы предусмотрен при замене транспорта.

**Почему 7 баз на одном сервере PostgreSQL?** База и инстанс не тождественны: семь отдельных DATABASE и семь пользователей, каждый подключается только к своей. На учебном окружении один контейнер экономит ресурсы, не нарушая владение данными.

**Чем GraphQL отличается от SQL?** SQL — внутренний язык чтения одной БД. GraphQL — внешний типизированный API, где клиент выбирает поля, а resolver обращается к нужному сервису и собирает ответ.

**Как связаны данные разных сервисов без внешних ключей?** Через UUID и MockRpcPorts. Например, Booking.lesson через отдельную операцию GetLesson, а рейтинг Teacher.rating через Reputation.

**Что такое Query?** Чтение без изменения состояния. Поэтому реальное бронирование или платёж не входят в ЛР3. Mutation оставлены в схеме, чтобы сохранить договорённый контракт, и возвращают явную ошибку NOT_IMPLEMENTED_IN_LAB3.

**Как обеспечивается доступ?** Заголовок Bearer → A.ValidateSession → проверка хеша сессии, времени и статуса → actor.role в resolver. Сервисы читают только записи, относящиеся к actor.id (например `student_id`).

**Что происходит при неизвестном id?** Nullable Query `teacher` возвращает `null`, а коллекции возвращают пустой список. Неверные UUID, пагинация и интервалы дают BAD_USER_INPUT.

**Как работает сортировка?** Выбор значения enum соответствует одному фиксированному выражению ORDER BY в каталоге, произвольный текст SQL от клиента не используется.

**Почему SQLAlchemy Core, а не ORM-сущности?** В ЛР2 заданы точные структуры и SQL; Core позволяет использовать их напрямую и не допустить расхождения `models` с подготовленным DDL. Репозиторные функции инкапсулируют обращения к БД.
