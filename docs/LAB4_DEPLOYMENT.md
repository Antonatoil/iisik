# ЛР4, вариант 27: независимое развёртывание семи внутренних сервисов

## Почему изменено

В предыдущем коммите семь сервисов были разными Python-модулями, но выполнялись
в одном процессе Gateway. Это не удовлетворяло требованию независимого запуска.
В этой доработке ЛР4 **коммит ЛР3 не изменяется**; в текущем коммите добавлен
отдельный FastAPI-процесс на каждый сервис.

## Состав

- `gateway` — HTTP/GraphQL 8000, Resolver и `workflows.py`; **образ `Dockerfile.gateway` не включает код сервисов или `db.py`**.
- `accounts`, `catalog`, `learning`, `payments`, `reputation`, `notifications`,
  `analytics` — семь отдельных Docker-контейнеров, каждый запускает
  `app.service_api:app` и разрешает только методы своего сервиса.
- `postgres` — один PostgreSQL с семью физическими базами и разными логинами.
- `tests` — **временный** контейнер профиля `test`, не часть платформы.

Внутренние приложения собираются по `Dockerfile.service` и запускаются отдельно.
Каждое приложение получает `SERVICE_OWNER` и может открыть только свою DB через
`app/core/db.py`. К контейнерам сервисов **не опубликованы порты хоста**.

## Mock-transport, не gRPC

Контракт `MockRpcPorts` сохранён. Gateway теперь вызывает по HTTP в Docker-сети
методы `/mock/{method}`. Это временный Mock-адаптер поверх HTTP, **не gRPC и не
Kafka**. Метод и сервис проверяются по allowlist в `rpc_registry.py`.
Все вызовы внутри сети защищены секретом `RPC_SHARED_KEY` из локального `.env`;
секрет не должен попадать в Git.

Query: Gateway -> Resolver -> MockRpcPorts -> HTTP -> сервис -> DB этого сервиса.

Mutation: Gateway -> Resolver -> MockRpcPorts -> workflow -> несколько HTTP Mock
вызовов -> собственные DB отдельных сервисов.

## Проверка преподавателем

```powershell
cd 'D:\бгуир\Иисик\iisik-github'
docker compose up -d --build
docker compose ps
Invoke-RestMethod http://localhost:8000/ready
docker compose run --rm tests
```

У работающего приложения — **9 контейнеров**: Gateway + семь сервисов + PostgreSQL.
Временный test-runner создаётся только на время проверки. Повторный запуск не
удаляет volume `tutor_db_data`.

Демонстрация самостоятельного рестарта, не затрагивающего остальные процессы:

```powershell
docker compose restart payments
docker compose ps
```

Демонстрация изоляции баз: `svc_a` не имеет CONNECT к базе `tutor_t`, а
`SERVICE_OWNER=a` запрещает вызов `engine('t')` на уровне приложения.

## Дополнительные исправления

1. Healthcheck PostgreSQL проверяет доступность СУБД через `pg_isready` вместо
   количества записей в тестовой таблице.
2. `/ready` Gateway проверяет семь независимых сервисов, не открывает их БД.
3. Ограничена поверхность внутреннего API (allowlist + общий секрет).
4. У сетевых вызовов есть таймауты и понятные ошибки `SERVICE_UNAVAILABLE`,
   `SERVICE_TIMEOUT`.
5. Денежные поля Decimal и даты с часовым поясом не теряют тип при передаче.
6. Конкурирующие повторения `operationId`, платежи одного бронирования и отзывы
   одного бронирования сериализуются через транзакционные advisory locks.
7. Обновление факта урока и популярности преподавателя в DB-X стало атомарным
   и не увеличивает версию повторно при одинаковом событии.
8. Вынесено тестирование в отдельный временный контейнер, не Gateway.

## Границы реализации

Нет настоящего gRPC, Kafka или распределённой ACID-транзакции. Вызовы проекций
и уведомлений в этой ЛР4 выполняются синхронно; при сбое одного из сервисов
возможны частично применённые изменения. Требуется Kafka/outbox для
полноценной eventual consistency в следующих лабораторных работах.
Данный патч **не обещает** распределённый rollback / Saga.

Не используйте `docker compose down -v`: эта команда удалит сохранённые базы.
