# Лабораторная №4 — вариант 27. Что показать на защите

Предыдущий проект: ЛР1 — архитектура, ЛР2 — контракты и SQL, ЛР3 — GraphQL Query + mock, ЛР4 — реализация 14 Mutation. Семь отдельных PostgreSQL БД, два контейнера (`gateway`, `postgres`), семь отдельных модулей сервисов. Никакого реального gRPC/Kafka пока нет.

## Как запустить

```powershell
docker compose up -d --build
docker compose ps
docker compose exec -T gateway python -m pytest -q
```

Открыть http://localhost:8000/graphql/ и вкладку Headers:

```json
{"Authorization": "Bearer demo-student-token"}
```

В `demo/lab4.graphql` представлены операции с переменными. Лучше показать: `teachers` с сортировкой, `platformAnalytics` под администратором, регистрацию/вход новой учётной записи, создание слота преподавателя, бронирование, симулированную оплату, повтор operationId, отмену/перенос с проверкой `expectedVersion`, обновление `notifications`.

## Где что в коде

- `contracts/schema.graphql`: контракт **не менялся относительно ЛР2**, все 14 Mutation уже присутствовали.
- `app/main.py`: FastAPI и аутентификация HTTP Bearer через A.
- `app/gateway/schema.py`: Resolver для 14 Query и 14 Mutation, только обработка GraphQL и передача управления через порты.
- `app/transport/mock_ports.py`: макет gRPC-интерфейсов, одинаковые именованные операции.
- `app/transport/workflows.py`: последовательность обращений к сервисным интерфейсам для сценариев с несколькими владельцами БД, **без SQL**.
- `app/services/*_write.py`: команды бизнес-области с транзакциями PostgreSQL, проверками и подготовкой ответа.
- `app/core/commands.py`: валидаторы и идемпотентные квитанции `command_receipts`.
- `app/core/db.py`: отдельные подключения к 7 БД, как в ЛР3.
- `tests/test_lab4.py`: сквозной тест создания данных, бронирования, оплаты, переноса, отмены, завершения и отзыва.

## Важные детали

`bookLesson`: T проверяет активность предмета/профиля, L в транзакции блокирует временной интервал преподавателя, проверяет пересечения ученика и создаёт `lesson + booking`. Повтор команды с тем же `operationId` не создаёт дубль. Цена фиксируется в DB-L, при переносе не меняется.

`registerPayment`: это **учебная симуляция подтверждения оплаты**, без банка/эквайринга. DB-P сохраняет факт, DB-L отмечает запись оплаченной. Отмена оплаченного занятия не делает возврат. В будущих лабораторных асинхронную доставку фактов реализуют с Kafka.

`startLesson`: только преподаватель, только оплаченное занятие в назначенном интервале. `completeLesson`: только `IN_PROGRESS`, преподаватель фиксирует текст и результат. `addReview`: только студент по собственному завершённому занятию и лишь один отзыв на запись. DB-R локально атомарно обновляет рейтинг.

`expectedVersion`: защита от изменения занятия по устаревшим данным. `operationId`: защита от случайного повторного выполнения команды. Ролевая авторизация проверяется при входе в Resolver, владельцы данных дополнительно проверяют идентификаторы.

## Техническое ограничение ЛР4

Семь БД не поддерживают единую распределённую транзакцию. Межсервисное обновление проекций X/T и формирование уведомлений N сделано **синхронным Mock-оркестратором**, а не гарантированным Kafka-консьюмером. При аварии после коммита владельца может потребоваться повторная доставка/восстановление. В ЛР5+ это следует улучшить реальным gRPC, outbox/inbox и брокером событий; не выдавать нынешний mock за гарантированную доставку.

Код демонстрационного входа поддерживает старые учебные SHA256-хеши ЛР3 и повышает их до PBKDF2 на успешной проверке; новые пароли сразу хешируются PBKDF2. Демо-токены и учётные данные не предназначены для производства.
